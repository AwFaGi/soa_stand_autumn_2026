## Идея

Вы пишете один сервис — **Orders**, оформление заказов маркетплейса — на любом
языке: Python, Java, Kotlin, C#, Go, TypeScript и др. Остальное есть в стенде:
база данных, заглушки Payment и Inventory и раннер сценариев, который проверяет
систему снаружи, как чёрный ящик.

Бизнес-процесс, жизненный цикл заказа, правила и требования к сервису —
[docs/SERVICE.md](docs/SERVICE.md).

Раннер проверяет только свойства системы: сколько раз списаны деньги, дошёл ли
заказ, уложился ли ответ по времени. Язык и внутреннее устройство сервиса он не
видит. Требования задают результат, способ решения выбираете вы.

## Что в стенде

```
docker-compose.yml
├── postgres     база для вашего сервиса (PostgreSQL 16)
├── mocks        заглушки Payment и Inventory, шина событий (задание 2)
├── orders       ВАШ сервис, собирается из ./orders/Dockerfile
└── runner       сценарии отказов, запускается отдельно: make scenarios
```

По команде раннера заглушки имитируют отказы: отвечают ошибкой, отвечают с
задержкой, пропадают из сети, теряют ответы. Список отказов — в таблицах
сценариев задания.

В `orders/` есть пример **наивной** реализации Orders. Он работает, пока
Payment и Inventory без отказов, и проваливает сценарии с отказами. Его можно взять за основу
или написать сервис с нуля — см. [«Наивный пример и свой язык»](#наивный-пример-и-свой-язык).

## Контракт вашего сервиса

Сервис слушает порт из переменной `PORT` (по умолчанию `8080`) и получает
адреса через переменные окружения:

| Переменная | Что это |
|---|---|
| `DATABASE_URL` | строка подключения к Postgres, база `orders` — ваша, схему создаёте сами |
| `PAYMENT_URL` | заглушка Payment |
| `INVENTORY_URL` | заглушка Inventory |
| `EVENTS_URL` | шина событий — нужна только для задания 2 |

Эндпоинты, которые вызывает раннер:

| Метод и путь | Что делает |
|---|---|
| `GET /healthz` | `200`, когда сервис готов принимать заказы |
| `POST /orders` | оформить заказ, тело ниже |
| `GET /orders/{id}` | текущее состояние заказа |
| `POST /webhooks/delivery` | задание 2: шина доставляет событие `delivery.confirmed` |
| `GET /users/{id}/bonus` | задание 2: бонусный баланс покупателя |

```json
POST /orders
{"user_id": "u-17", "items": [{"sku": "sku-1", "qty": 2, "price_cents": 49900}]}

→ 201 {"id": "…", "status": "paid"}
```

`id` из ответа на `POST /orders` — это тот же `order_id`, который сервис
передаёт в Payment и Inventory: по нему раннер сверяет факты заглушек с
заказами.

Статусы заказа:

| Статус | Смысл |
|---|---|
| `paid` | товар зарезервирован, деньги списаны |
| `rejected` | заказ не состоялся: денег не взяли, резерва нет |
| `pending` | исход ещё неизвестен, сервис продолжает разбираться |

Коды ответа:

- `POST /orders` отвечает `201` с любым из трёх статусов — в том числе когда
  Payment или Inventory недоступны. `400` — только на некорректное тело. `5xx` раннер считает
  ошибкой.
- `GET /orders/{id}` отвечает `200 {"id", "status", "amount_cents"}` или `404`.

**`pending` — допустимый ответ.** Сервис не обязан знать исход к моменту
ответа на `POST`: он может ответить `pending` и завершить обработку заказа в
фоне. После нагрузки раннер ждёт и проверяет итог через `GET /orders/{id}`.
Ограничение по времени из задания относится только к HTTP-ответу на `POST`;
фоновая обработка может длиться дольше.

Полный контракт — [`contracts/orders.yaml`](contracts/orders.yaml). Контракты
Payment, Inventory и шины событий лежат там же: [`payment.yaml`](contracts/payment.yaml),
[`inventory.yaml`](contracts/inventory.yaml), [`events.yaml`](contracts/events.yaml).
В них описаны все их возможности.

## Как запускать

Нужно: Docker с Compose v2, git, make. На Windows — WSL2. Язык и его
инструменты — ваши.

Если `make up` падает с `client version … is too old. Minimum supported API
version is …`, плагин Compose старее, чем Docker: обновите Docker Compose или
запускайте с версией API из сообщения, например
`DOCKER_API_VERSION=1.44 make up`.

```sh
make up                      # запустить стенд вместе с вашим сервисом
make scenarios TASK=1        # запустить сценарии задания 1
make scenarios TASK=2        # задания 2 (необязательного): S1, S6–S8
make scenarios ONLY=S3       # один сценарий (или несколько: ONLY=S2,S5)
make ui                      # дашборд заглушек с кнопками управления стендом
make docs                    # контракты в Swagger UI (http://localhost:8091)
make logs                    # логи всех контейнеров
make down                    # остановить
make help                    # все команды
```

Раннер выводит по каждому сценарию `PASS` или `FAIL` и журнал фактов: число
запросов к Payment, число списаний по каждому заказу.
По журналу определяется причина провала.

Те же результаты `make scenarios` кладёт в `results/`: `task_1.txt` — вывод
раннера, `task_1.html` — отчёт для браузера: проверки, журнал фактов, время
ответа на `POST /orders` и по каждому проблемному заказу — все его запросы к
Payment и Inventory по времени.

`make ui` печатает ссылку на дашборд заглушек и открывает её. Дашборд
обновляется раз в секунду: текущий сценарий, режимы Payment и шины, запросы к
Payment, Inventory и шине по мере их прихода, списания, резервы и события
`order.paid` по каждому заказу. В таблице заказов колонка «Событие» — приняла
ли шина событие по заказу; флаги «paid без события» и «разные id события»
отмечают проблемные заказы задания 2.
Работает и при ручных запросах к сервису, без раннера.

Сверху на дашборде — панель управления стендом:

- **Режимы Payment** — доля ответов 500, доля отказов банка (402), задержка
  ответа, «не отвечает N секунд», потеря ответа после списания. Кнопки
  «как в S1…S5» выставляют режимы и темп заказов из открытых параметров
  сценария. «Убрать все отказы» возвращает в штатный режим и Payment, и шину.
  «Очистить журнал» начинает журнал заглушек заново.
- **Шина событий** (задание 2) — «недоступна N секунд, начиная через M»,
  доля висящих запросов во время отказа; «как в S6» выставляет режимы шины и
  Payment и темп заказов сценария S6. «Применить» в панелях Payment и шины
  меняет только свою часть: режимы соседней панели сохраняются.
- **Заказы в Orders** — отправить один заказ или поток из N заказов с
  заданным темпом; ответы вашего сервиса видны в ленте и в таблице заказов,
  «Проверить статусы» запрашивает `GET /orders/{id}` по этим заказам.
- **Доставка** (задание 2) — шина присылает в `POST /webhooks/delivery`
  N событий `delivery.confirmed` для K покупателей, каждое — до C копий,
  часть копий одновременно; «Прислать копии ещё раз» — ещё по одной копии
  каждого события. «Проверить балансы» сравнивает `GET /users/{id}/bonus` с
  ожидаемым по каждому покупателю и по `u-0`, которому событий не было;
  «ожидалось» — сумма по всем партиям с момента `make up`.
- **Проверка сценариями** — те же проверки, что `make scenarios`: задание 1
  (все сценарии или один) или задание 2 (S1 и S6; S7 и S8 — только
  `make scenarios TASK=2`), пауза после заказов 30 с (как на проверке) или 5 с
  для отладки. Ход прогона, `PASS`/`FAIL`, уровень и HTML-отчёт выбранного
  задания — на дашборде; результаты пишутся в `results/ui_task_N.*` (отчёт
  `make scenarios` — `results/task_N.*` — не затирается).

Пока идёт прогон сценариев — из дашборда или `make scenarios`, — ручные
кнопки дашборда недоступны: ручные режимы, «Очистить журнал» и заказы
испортили бы проверку. Заглушки отвечают на такие действия со страницы
кодом `409` с текстом «Идёт прогон сценариев…». Начало прогона прерывает
отправку заказов с дашборда. Если прогон прервать (Ctrl+C), кнопки
возвращаются сразу; если раннер оборвался, не успев отметить конец, —
примерно через 2,5 минуты.

Два прогона сразу не идут: `make scenarios` (и `make up`) откажется
запускаться, пока идёт прогон из дашборда или другой `make scenarios`, а
кнопки прогона на дашборде недоступны во время `make scenarios`. `make down`
останавливает и сервис прогонов дашборда.

Полный прогон задания 1 занимает около четырёх минут: после каждого сценария
раннер ждёт 30 секунд, пока сервис завершает обработку заказов. Для отладки
паузу можно сократить: `make scenarios ONLY=S3 WAIT=5`. Итоговую проверку
запускайте с паузой по умолчанию. Прогон задания 2 — около пяти минут; в S7 и
S8 `make scenarios` сам перезапускает контейнер `orders`, поэтому эти
сценарии запускаются только из `make scenarios`, не из дашборда.

На хосте открыты порты `127.0.0.1:8080` (ваш Orders), `127.0.0.1:8090`
(заглушки и дашборд) и, после `make docs`, `127.0.0.1:8091` (контракты).
Сервис можно вызвать вручную:

```sh
curl -s localhost:8080/orders -d '{"user_id":"u-1","items":[{"sku":"sku-1","qty":1,"price_cents":100}]}'
```

Управление заглушками (`/admin/*`) закрыто токеном: `make` создаёт его один
раз в файле `.mocks-token` (в git не попадает), ссылка из `make ui` уже
содержит его. Для своих экспериментов с `/admin/modes` — токен: `make token`.

Изменяющие запросы к `/admin/*` (`PUT /admin/modes`, `POST /admin/reset`)
принимаются только с заголовком `Content-Type: application/json`, иначе —
`415`:

```sh
curl -s -X PUT localhost:8090/admin/modes -H "X-Admin-Token: $(make -s token)" \
  -H 'Content-Type: application/json' -d '{"payment":{"fail_rate":0.5}}'
```

Обращайтесь к заглушкам по `localhost` или `127.0.0.1`: на другое имя хоста
`/admin/*` отвечает `403`.

Стенд с пустым токеном (`make up MOCKS_ADMIN_TOKEN=`) открывает `/admin/*` без
заголовка. `make ui` без `MOCKS_ADMIN_TOKEN=` пересоздаёт заглушки с токеном
из `.mocks-token` — открытый `/admin/*` пропадает; чтобы сохранить его,
запускайте и `make ui MOCKS_ADMIN_TOKEN=`.

База доступна изнутри стенда: `docker compose exec postgres psql -U orders orders`.
Она живёт в памяти: `make up` и `make scenarios` пересоздают базу и
перезапускают ваш сервис, каждый прогон начинается с пустой базы.

## Наивный пример и свой язык

В `examples/` лежат две наивные реализации с одинаковым поведением:
`examples/go/` (`net/http` и `pgx`) и `examples/python/` (стандартная библиотека
и `psycopg`). В `orders/` скопирован Go-пример.

Взять Python-пример вместо Go:

```sh
rm -rf orders && cp -r examples/python orders
```

Свой язык: удалите содержимое `orders/` и положите туда свой код и
`Dockerfile`. Требования к образу:

- собирается командой `docker build orders/` без аргументов;
- при старте слушает порт из `PORT` и берёт адреса из переменных окружения
  (см. «Контракт вашего сервиса»);
- схему базы создаёт сам при старте — база `orders` пустая;
- `GET /healthz` отвечает `200`, когда сервис готов. Раннер ждёт его до двух
  минут после `make up`.

Попробовать пример, не трогая `orders/`: `make scenarios ORDERS_DIR=./examples/python`.
Проверка всегда собирает `orders/`.

## Как сдавать

1. Форк `ippaveln/soa_stand_autumn_2026` на GitHub. Основная ветка — `master`.
2. В форке включите Actions: вкладка **Actions** → **I understand my workflows,
   go ahead and enable them**. После этого каждый push в `master` форка
   собирает ваш сервис и запускает сценарии; результат — на вкладке
   **Actions**.
3. Ваш код — в директории `orders/`, вместе с `Dockerfile`. Остальные
   директории не меняйте: любое изменение вне `orders/` (кроме `.gitignore`)
   проваливает задание.
4. Один pull request из `master` форка в `master` исходного репозитория.
   Заголовок — `ИСУ <номер>`, например `ИСУ 123456`.
5. CI собирает ваш образ и запускает сценарии обоих заданий. Результат —
   checks `task_1` и `task_2 (необязательное)` в PR. Check зелёный только на
   уровне «полностью»: на уровне «засчитано» `task_1` красный, а уровень
   виден в строке `Уровень:` вывода раннера (в summary check). Как устроена
   проверка — [GRADING.md](GRADING.md).
6. Описание PR — по шаблону ниже (подставляется автоматически), коротко.
7. Защита устная: 5–10 минут, вопросы по вашему решению.

Задание 1 обязательное, выдаётся 30.09. Срок — 26.10, 23:59 МСК: к этому
моменту PR открыт и задание выполнено. Допуск к экзамену — задание 1 засчитано
(уровень «засчитано» в [`docs/TASK_1.md`](docs/TASK_1.md)) и защита пройдена.

Задание 2 необязательное: на допуск не влияет. Кто выполнит задание 2 на уровне «полностью», задание 1 на уровне «полностью» и защитит оба, получает экзамен автоматом. Срок
задания 2 — 27.10, 23:59 МСК. Делается в том же PR и в той же `orders/`; на
защите спросят и про него.

CI в PR гоняет сценарии с открытыми параметрами — теми же, что
`make scenarios`. Перед защитой сценарии дополнительно прогоняются с другими
параметрами: другие доли ошибок, задержки и момент отказа. Решение,
подобранное под числа открытого прогона, там не пройдёт: проверяются свойства
из требований при других значениях параметров.

### Обновления стенда

Исправления стенда (заглушки, раннер, `Makefile`, описание) приходят в
`master` исходного репозитория. Официальная проверка всегда берёт стенд
оттуда, поэтому подтягивайте обновления в форк, чтобы локально проверять
тем же стендом.

На GitHub: страница форка → **Sync fork** → **Update branch**. Или из
терминала:

```sh
git remote add upstream https://github.com/ippaveln/soa_stand_autumn_2026.git  # один раз
git pull upstream master
git push origin master
```

Обновления не трогают `orders/`, поэтому конфликтов не будет, если вы меняли
только `orders/`. Если GitHub предлагает **Discard commits** — не
соглашайтесь: это удалит ваши коммиты; значит, в форке изменено что-то вне
`orders/`, верните эти файлы как в исходном репозитории.

## Шаблон PR

Три раздела, в каждом — несколько строк или короткий список.

1. **Что сделано и почему.** Какую проблему решали, какое решение выбрали,
   что ещё рассматривали и почему отказались.
2. **Что будет при отказе.** Для каждого обращения Orders к другому сервису
   (Payment, Inventory; если делали задание 2 — шина событий и входящие
   события): что происходит, если сервис ответил ошибкой, не ответил вовсе,
   ответ потерялся, а для задания 2 — ещё и если Orders упал посреди работы.
   Чем заплатили за решение: сложность, задержка, лишние запросы, что может
   сломаться теперь.
3. **Проверка.** Вывод раннера. Если есть свои тесты или замеры — сюда же.

## ИИ

Разрешён без ограничений: писать код, разбираться в языке, читать контракты.
Отвечаете за решение вы. На защите вопросы вида «что будет, если упасть вот
в этой строке», «откуда вы знаете, что деньги не спишутся дважды». Если
объяснить собственный код не получается, задание не засчитывается.
